# Documentation & Comments

給「其他人會讀到」的產物用的規則：程式碼註解、commit message、測試描述、
MR 描述、交付文件。內部追蹤文件（`TKT-*`、handoff、changelog）的建立與維護
規則在 `docs-management` skill，不在這裡。

## 內部行話不外流
程式碼註解、commit message、測試描述、MR 描述中，不得出現只有我們懂的內部
參照——`TKT-*`、D-編號、`AC-*`、DESIGN / ANALYSIS 等文件代號。讀這些的是
沒有那個 context 的其他開發者，看到代號只會卡住。

一律改寫成不依賴外部脈絡也讀得懂的敘述。真的需要追溯，寫在 MR 描述的獨立
段落或 ticket 裡，不要混進程式碼。

## 寫給讀的人
註解、commit message、MR 描述與報告，用白話、精簡的句子寫給實際會讀的人；
MR 描述的讀者是要 review 的開發者。不服務讀者的內容就刪掉。
報告正文第一次出現術語時保留原文、帶一句白話；完整的術語解釋集中放在文末。
GitLab 的 MR 描述與留言裡，MR 和 issue 參照寫成純文字（例如 group/repo!123），不加反引號，才會自動連結。

## 交付文件只寫最終正確事實
交付文件只寫當下正確的結論。不留先前錯誤陳述的痕跡、不留「我之前說錯了」
的修正敘事、不留思路變更紀錄。修正過程留在對話裡——文件是給讀者的，
不是給我自己的紀錄。

同理：除非明確要求，不產出額外格式的 artifact（HTML、有樣式的報告）。
一次請求一份交付物。

## 註解克制
只在必要時加註解；程式碼本身無歧義就不加。

production（非測試）程式碼中，移除這三種：已經被測試涵蓋的、
只是複述這次改動的、以及拿掉也不會讓其他開發者誤解的。
